Typed Routes

Use the generated PageProps, LayoutProps and RouteContext types, check links with typedRoutes, and generate types in CI with next typegen.

NNext.jsCurrentTargets Next.js 16.3

Overview#

Next.js reads your app/ folder and generates TypeScript types that describe it. There are two separate features:

FeatureWhat it typesHow to turn it on
Route props helpers: PageProps, LayoutProps, RouteContextparams, searchParams, children and slot props of pages, layouts and route handlersAlways available once types are generated
Statically typed links: typedRouteshref on <Link>, and push, replace and prefetch on useRouter()typedRoutes: true in next.config.ts

Both are generated by next dev, next build, or next typegen. The helpers are global types: you use PageProps<'/blog/[slug]'> without importing anything.

Why it exists#

Writing { params: Promise<{ slug: string }> } by hand repeats information the file system already holds, and it drifts. Rename [slug] to [postSlug] and the hand-written type still compiles while the page receives undefined. A generated type fails to compile instead.

Links have the same problem in the other direction. A typo in href="/setings" is a 404 that no test catches until someone clicks it. With typedRoutes, it is a compile error.

When to use it#

  • Use PageProps, LayoutProps and RouteContext on every page, layout and route handler in a TypeScript project. There is no configuration cost.
  • Turn on typedRoutes once your routes are reasonably stable, so broken links surface in the editor and in CI.
  • Run next typegen before tsc --noEmit in CI, where you do not want to run a full build only to type-check.

When not to use it#

Do not hand-write params types in new code. They cannot detect a renamed folder.

Do not expect typedRoutes to validate links that proxy rewrites or redirects create. It only knows about files in app/. Cast those with as Route.

Do not rely on the generics to validate data. PageProps says slug is a string. It cannot tell you the string is a real post.

Basic example#

app/blog/[slug]/page.tsx
export default async function BlogPostPage({ params, searchParams }: PageProps<'/blog/[slug]'>) {
  const { slug } = await params
  const { ref } = await searchParams
  return (
    <h1>
      {slug}
      {typeof ref === 'string' && <small> (via {ref})</small>}
    </h1>
  )
}
app/dashboard/layout.tsx
export default function DashboardLayout(props: LayoutProps<'/dashboard'>) {
  // If app/dashboard/@analytics exists, props.analytics is typed too.
  return <section>{props.children}</section>
}
app/api/projects/[projectId]/route.ts
import type { NextRequest } from 'next/server'

export async function GET(_request: NextRequest, context: RouteContext<'/api/projects/[projectId]'>) {
  const { projectId } = await context.params
  return Response.json({ projectId })
}

The string you pass is the route, not the file path: route groups like (shop) and slots like @modal do not appear in it. The generic only accepts routes that exist, so PageProps<'/blgo/[slug]'> is a compile error.

How it works#

Generation#

Next.js writes the declarations into its output directory (.next/types for next build and next typegen, .next/dev/types for next dev) and a next-env.d.ts file at the project root that references them. The tsconfig.json that create-next-app writes already includes both.

next typegen generates the same types without building:

bash
npx next typegen
npx tsc --noEmit

A typical package.json script:

package.json
{
  "scripts": {
    "typecheck": "next typegen && tsc --noEmit"
  }
}

Without that first step, a fresh CI checkout has no generated types, and every PageProps reference fails with "Cannot find name".

Tip

next-env.d.ts is generated and belongs in .gitignore. next typegen loads next.config.ts using the production build phase, so any environment variables the config reads must be available in CI.

What each helper contains#

HelperProperties
PageProps<Route>params: Promise<…>, searchParams: Promise<Record<string, string \| string[] \| undefined>>
LayoutProps<Route>params: Promise<…>, children: React.ReactNode, plus one React.ReactNode per parallel route slot
RouteContext<Route>params: Promise<…>

Static routes resolve params to {}. Dynamic segments map to string, catch-all segments to string[], and optional catch-all segments to string[] | undefined. See dynamic segments.

Statically typed links#

Enable typedRoutes in the config:

next.config.ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  typedRoutes: true,
}

export default nextConfig

Note

typedRoutes is a stable top-level option. Older guides put it under experimental.typedRoutes, which is no longer the place for it.

Next.js then generates a Route type listing every page in app/ and uses it for href on next/link and for push, replace and prefetch on useRouter() from next/navigation. Literal strings and template literals are both checked:

app/ui/account-menu.tsx
'use client'

import Link from 'next/link'
import { useRouter } from 'next/navigation'

export function AccountMenu({ teamSlug }: { teamSlug: string }) {
  const router = useRouter()

  return (
    <nav>
      <Link href="/settings">Settings</Link>
      <Link href={`/teams/${teamSlug}`}>Your team</Link>
      <button type="button" onClick={() => router.push('/billing')}>
        Billing
      </button>
    </nav>
  )
}

A link to a route that does not exist fails to compile:

<Link href="/setings">Settings</Link>
// TypeScript error: "/setings" is not assignable to the generated route type,
// because there is no app/setings/page.tsx.

For a string that TypeScript cannot see as a literal, cast it with the Route type from next:

app/ui/recent-link.tsx
import type { Route } from 'next'
import Link from 'next/link'

export function RecentLink({ path, label }: { path: string; label: string }) {
  // `path` comes from the database, so TypeScript cannot check it.
  return <Link href={path as Route}>{label}</Link>
}

Every cast is a place the compiler stops helping, so keep them at the boundary where untyped data enters.

Common patterns#

A navigation config checked against real routes#

app/ui/nav-items.ts
import type { Route } from 'next'

type NavItem = { href: Route; label: string }

export const navItems: NavItem[] = [
  { href: '/', label: 'Home' },
  { href: '/blog', label: 'Blog' },
  { href: '/settings', label: 'Settings' },
]

With typedRoutes on, deleting app/settings/page.tsx turns the third entry into a compile error instead of a dead menu link.

A component that wraps Link#

Accept the route type through a generic, so callers keep literal checking:

app/ui/card-link.tsx
import type { Route } from 'next'
import Link from 'next/link'
import type { ReactNode } from 'react'

export function CardLink<T extends string>({ href, children }: { href: Route<T>; children: ReactNode }) {
  return (
    <Link href={href} className="card">
      {children}
    </Link>
  )
}

Checking a runnable app#

The routing example app enables typedRoutes and runs next typegen && tsc --noEmit as its typecheck script.

Common mistakes#

Running tsc in CI without next typegen first. The global helpers do not exist until types are generated, so every page fails with "Cannot find name 'PageProps'".

Passing a file path instead of a route. PageProps<'/(shop)/cart'> is wrong. Groups and slots are not part of the URL: write PageProps<'/cart'>.

Importing PageProps from next. The route-aware helpers are globals. There is nothing to import.

Committing next-env.d.ts. It is regenerated on every run and belongs in .gitignore.

Casting every href to Route. A blanket cast turns the feature off. Cast only strings that genuinely come from outside the code.

Expecting typed links to know about proxy rewrites. A URL served only through proxy.ts is not a file in app/, so it needs a cast.
