Next.js learning path

An ordered route through the React prerequisites and all seventeen Next.js groups, from a first route to a production deploy.

NNext.jsCurrentTargets Next.js 16.3

This path assumes you are building an App Router app on Next.js 16.3. Each stage names the first page of a group. Read that page, then continue through the group in sidebar order before moving on. The order is not arbitrary: caching makes no sense before rendering, and security makes no sense before mutations and backend features.

Stage 0 — React first#

Next.js pages do not re-explain React. If any of these are unfamiliar, read them before Stage 1. The full React route is the React learning path.

  • Introduction to React and Thinking in React — the component model everything else assumes.
  • State, useEffect and Composition — the client-side vocabulary. The "when not to use it" part of useEffect matters more in Next.js, where most data loading moves to the server.
  • Suspense — the loading boundaries Next.js streams around.
  • Server React, Server Components, Directives and Server Functions — the React model the App Router is built on. Do not skip these.
  • Forms and Actions and Error boundaries — what Server Actions and error.tsx build on.
  • TypeScript setup — the React type packages every Next.js project installs.

Stage 1 — Getting started#

  1. Introduction to Next.js — what the framework adds, and the React Canary build the App Router runs.
  2. Installation — a running app on 16.3.5, above the security floor.
  3. Project structure — which file names are API.
  4. Dev and build — next dev, next build, Turbopack.
  5. TypeScript in Next.js — generated route types.
  6. AI coding agents — AGENTS.md and the bundled docs, if you work with an agent.

Stage 2 — Routes and rendering#

  • Routing. Start at File conventions. Folders become URLs, layouts nest, and params is a Promise.
  • Rendering. Start at Server Components in Next.js. Where code runs, what is prerendered, and React Canary in Next.js.
  • Errors and loading UI. Start at Error boundaries. error.tsx, catchError, notFound() and loading.tsx.

Stage 3 — Data#

  • Data and caching. Start at Caching model. Cache Components, "use cache", cacheLife and revalidation. The most important group for performance and the one old tutorials get most wrong.
  • Mutations. Start at Server Actions. Forms, revalidating after a write, and optimistic updates.
  • Databases and ORMs. Start at Databases overview. Connection pooling, Prisma and Drizzle.

Stage 4 — Backend and security#

  • Backend features. Start at Route Handlers. Then proxy.ts, runtimes, environment variables, webhooks and background work.
  • Authentication and authorization. Start at Auth overview. Sessions, a data access layer and protecting routes.
  • Security. Start at Security overview. Read it before you deploy anything with a Server Action in it. Keep Security advisories bookmarked.

Stage 5 — Polish and speed#

  • Styling, images, fonts and metadata. Start at CSS and Tailwind.
  • Performance. Start at Performance overview. Measure before changing anything.
  • Instant Navigations. Start at Instant Navigations overview. This is opt-in in 16.3 and requires Cache Components, so read it after the data and caching group.

Stage 6 — Ship it#

  • Testing. Start at Testing overview. Unit tests for components, and Playwright for everything that needs a server.
  • Deployment. Start at Build output, and finish with the deployment checklist.

Stage 7 — Existing apps and reference#

  • Migration. Start at Next.js 15 to 16. Read it if you maintain an older app, or whenever a tutorial's code does not compile.
  • Reference. Start at File conventions reference. Not reading material: the cheat sheet and troubleshooting are for bookmarking.

Common mistakes#

  • Starting with Next.js before Server Components make sense. The App Router is Server Components plus conventions. Without Stage 0 the conventions look arbitrary.
  • Learning caching from a pre-16 tutorial. Implicit fetch caching and route segment exports like revalidate belong to the previous model. Learn Cache Components from the data and caching group, and use the migration group only for old code.
  • Treating proxy.ts as the place for authorization. Read the auth and security groups before protecting anything.
  • Enabling Instant Navigations first. It is opt-in and builds on Cache Components. Get caching right, then opt in.
  • Skipping testing until the end of a project. Server Actions and Route Handlers are public endpoints, and tests are how you prove their checks work.
