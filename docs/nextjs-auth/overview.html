Authentication and authorization overview

Authentication, session management and authorization in a Next.js 16.3 app, and which layer is allowed to make the final decision.

NNext.jsCurrentTargets Next.js 16.3

Overview#

Auth in a Next.js app is three separate jobs, and most security bugs come from doing one of them in the wrong place:

JobQuestion it answersWhere it lives in Next.js
AuthenticationWho is this person?A Server Action (or an auth library's Route Handler) that checks credentials
Session managementHow do we remember them on the next request?A signed or encrypted cookie, set with await cookies() in a Server Action or Route Handler
AuthorizationMay this user read or change this data?The Data Access Layer (DAL), on every request, next to the data

This group documents all three for the App Router in Next.js 16.3:

  • Sessions: stateless cookies with jose versus database sessions, and the cookie attributes that matter.
  • Auth libraries: Better Auth, Auth.js (beta) and hosted providers, and why each still needs your DAL.
  • Data Access Layer: the authoritative pattern, with server-only, verifySession() in React cache(), and DTOs.
  • Protecting routes: what proxy.ts is for, and what it cannot do.
  • Role-based access: roles, permissions, and the experimental forbidden() / unauthorized().

Every page is backed by the runnable auth example app.

Why it exists#

A single-page app has one entry point: the JavaScript bundle. If the router hides a screen, the user never sees it, and the real checks live in a separate API.

A Next.js app has many entry points in one codebase. Every page, every Server Action and every Route Handler is reachable directly over HTTP. proxy.ts runs in front of some of them, depending on its matcher. So the question is not "where do I put the auth check" but "which of these layers is allowed to be the one that says no".

The answer this site gives, following the official Next.js guides, is: proxy.ts and layouts give fast, optimistic redirects for a better user experience. The DAL makes the authoritative decision, close to the data, every time.

When to use it#

Read this group when you are:

  • adding sign-in to an App Router app, with or without a library,
  • deciding where session checks go before writing the first protected page,
  • reviewing an app whose only protection is proxy.ts or a check in a layout,
  • adding roles to an app that so far only distinguished signed in from signed out.

When not to use it#

This group does not teach the React side of forms and Server Functions. For useActionState, pending state and form resets, see Forms and actions. For the exploit walkthroughs, see the Security group. For an identity protocol such as OAuth or OpenID Connect, follow your provider's documentation. A library or hosted provider should implement those flows, not your app.

Basic example#

The whole chain in four files. Each is shown in full on its own page.

A Server Action authenticates and creates the session:

app/actions/auth.ts
'use server';

import { redirect } from 'next/navigation';
import { checkCredentials } from '@/lib/users';
import { createSession } from '@/lib/session';

export async function login(formData: FormData) {
  const email = String(formData.get('email') ?? '');
  const password = String(formData.get('password') ?? '');

  const user = await checkCredentials(email, password);
  if (!user) {
    return;
  }

  await createSession(user.id, user.sessionVersion);
  redirect('/dashboard');
}

The DAL verifies the session once per request:

lib/dal.ts
import 'server-only';

import { cache } from 'react';
import { cookies } from 'next/headers';
import { decrypt } from '@/lib/session';
import { findUserById } from '@/lib/users';

export const verifySession = cache(async () => {
  const token = (await cookies()).get('session')?.value;
  const payload = await decrypt(token);
  if (!payload) return null;

  const user = await findUserById(payload.userId);
  if (!user) return null;

  return { userId: user.id, role: user.role };
});

A page uses the DAL, not the cookie:

app/dashboard/page.tsx
import { redirect } from 'next/navigation';
import { verifySession } from '@/lib/dal';

export default async function DashboardPage() {
  const session = await verifySession();
  if (!session) redirect('/login');

  return <h1>Your dashboard</h1>;
}

And proxy.ts redirects signed-out browsers early, without being trusted:

proxy.ts
import { NextResponse, type NextRequest } from 'next/server';

export function proxy(request: NextRequest) {
  if (!request.cookies.has('session')) {
    return NextResponse.redirect(new URL('/login', request.nextUrl));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ['/dashboard/:path*'],
};

Delete proxy.ts and the app is exactly as secure as before. It only redirects sooner. That property is the test of a correct design.

How it works#

Where each check runs#

LayerRuns forCan it be skipped?Use it for
proxy.tsRequests its matcher matches, before routingYes: a matcher that omits a path, a moved Server Function, or a framework bugOptimistic redirects based on the cookie. No database calls.
LayoutThe first render of a segmentYes: layouts are kept, not re-rendered, on client navigationShowing session-derived UI, such as a user menu
PageEach render of that pageNo, for that pageRedirecting when the DAL returns no session
Server ActionEach POST that invokes the actionNo, but it is its own endpointCalling the DAL before any mutation
Route HandlerEach request to that routeNo, but it is its own endpointCalling the DAL and returning 401 / 403
DALEvery data read and write that goes through itOnly if code bypasses the DALThe authoritative authentication and authorization check

Why a layout is not an authorization boundary#

The official authentication guide gives two reasons.

First, partial rendering. On a client-side navigation, Next.js keeps shared layouts and replaces only the page below them. A session check in app/dashboard/layout.tsx runs when the user first enters /dashboard, and not again when they move to /dashboard/settings. The session could have expired or been revoked in between.

Second, a layout does not control whether the rest of the route renders. Pages and parallel route slots are rendered by the router. A layout that returns null or swaps out children for signed-out users does not stop those segments from running, or from appearing in the RSC payload.

And a layout check never covers a Server Action defined on a page below it: the action is a separate POST endpoint.

Why Server Actions and Route Handlers check for themselves#

A Server Action is a public HTTP endpoint. Next.js gives it an encrypted, non-deterministic ID and removes unused actions from the client bundle, but the data security guide is explicit that you must still treat every action as reachable by a direct POST. React says the same about Server Functions. A Route Handler is an ordinary HTTP endpoint that anyone can call with curl.

proxy.ts does not reliably stand in front of either. The proxy reference notes that Server Functions are handled as POST requests to the route where they are used, so a matcher that excludes that path also skips the action. A refactor that moves the action changes its coverage silently.

Server and client implications#

All of this code runs on the server. Client Components cannot import the DAL: mark it import 'server-only' so a mistaken import fails the build.

To show the user in a Client Component, read the session in a Server Component and pass only the fields the UI needs as props. Hiding a button in a Client Component based on those props is a user-experience decision, never an authorization decision. See Role-based access.

Caching implications#

Reading cookies() makes the code that reads it request-time work. With Cache Components enabled (cacheComponents: true), a plain "use cache" function cannot call cookies() or headers(). The bundled authentication-with-Cache- Components guide gives two options:

  • Resolve the user outside the cached scope, then pass only the user ID into a "use cache" function that is not exported, so no caller can pass another user's ID.
  • Use "use cache: private", which may read cookies() and headers() directly. Its results are not stored in a server cache across requests. They can be kept in browser memory for the cacheLife stale time.

With Cache Components, a component that reads the session must also sit behind a <Suspense> boundary. The Data Access Layer page shows the pattern, and use cache covers the directives.

Security considerations#

proxy.ts has been bypassed in the real world. The July 2026 Next.js security release fixed a proxy/middleware bypass with Turbopack and a single i18n locale (CVE-2026-64642), patched in 16.2.11, 15.5.21 and 16.3.0. An app whose only protection was proxy.ts was exposed. An app that authorized in its DAL was not. Run next@16.3.3 or later, and pin 16.3.5, for the later fixes in the security advisories.

The exploit walkthroughs are in Proxy is not authorization and Server Actions authorization.

Common mistakes#

Treating proxy.ts as the security boundary. It is optimistic. It sees a cookie, not a verified user, and its matcher decides what it covers.

Checking auth only in a layout. Layouts do not re-render on client navigation, and they do not stop nested pages or Server Actions from running.

Checking auth on the page but not in its Server Action. The action is a separate endpoint. A page-level redirect does not protect it.

Stopping at authentication. "Signed in" is not "allowed to edit invoice 42". Authorize per resource and per action, in the DAL.

Setting cookies while rendering. Cookies can be set only in a Server Action or Route Handler. A Server Component that tries to log a user out during render fails.

Returning whole database rows to components. Pass DTOs with only the safe fields, so a password hash cannot reach a Client Component through props.
