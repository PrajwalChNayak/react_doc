cacheLife and cacheTag

Set how long a cached entry stays fresh with cacheLife profiles, and name it with cacheTag so you can invalidate it on demand.

NNext.jsCurrentNext.js 16.0+Targets Next.js 16.3

Overview#

Every "use cache" scope has a lifetime and can carry tags. Both come from next/cache:

  • cacheLife(profile) sets the lifetime. The profile is a built-in name, a custom name from next.config.ts, or an inline object.
  • cacheTag(...tags) attaches one or more names to the entry, so revalidation can target it later.

Both can only be called inside a cache directive scope. Calling either at module scope throws.

Why it exists#

"How long is this data fresh?" has no single answer. A price list and a legal page need very different lifetimes, and the right answer also differs between the browser, the server and the prerendered HTML. cacheLife expresses all three with one call next to the data access, instead of spreading them across headers and config.

Time alone is also not enough. When an editor publishes a post, waiting for a timer is wrong. Tags give each entry a name that a mutation or a webhook can invalidate the moment the data changes.

When to use it#

  • cacheLife: in every "use cache" scope. The official recommendation is to always set it, so the lifetime is visible where the cache is declared.
  • A built-in profile when one matches how often the data changes.
  • A custom profile when several functions share a policy that the built-ins do not express, such as "catalog data".
  • cacheTag: on everything you might need to invalidate, which is almost everything.

When not to use it#

  • To make data "almost fresh". If a value must be correct on every request, do not cache it with a tiny lifetime. Leave it uncached behind <Suspense>.
  • Redefining a time-named built-in such as days to mean two hours. It is supported, but readers will assume the preset. Define a custom name instead.
  • Tags derived from unbounded input, such as a search query. Each distinct tag is metadata to track, and nothing will ever invalidate most of them.

Basic example#

lib/articles.ts
import { cacheLife, cacheTag } from 'next/cache';

export type Article = { slug: string; title: string; body: string };

export async function getArticle(slug: string): Promise<Article | null> {
  'use cache';
  cacheLife('days');
  cacheTag('articles', `article:${slug}`);

  const response = await fetch(`https://cms.example.com/articles/${encodeURIComponent(slug)}`);
  if (response.status === 404) return null;
  if (!response.ok) throw new Error(`CMS responded with ${response.status}`);
  return response.json();
}

The entry refreshes in the background after a day. Invalidating articles refreshes every article; invalidating article:getting-started refreshes one.

How it works#

The three timings#

A profile has three properties, all in seconds:

PropertyApplies toMeaning
staleThe browserHow long the client router reuses the result without asking the server. Also decides whether the result can be in the route's App Shell.
revalidateThe serverAfter this long, the next request is served the cached value and triggers a background refresh.
expireThe serverAfter this long without requests, the next request waits for fresh content instead of receiving the old value. Must be longer than revalidate.

revalidate gives you stale-while-revalidate. expire is the upper bound on how old a served value can be after a quiet period.

Built-in profiles#

ProfilestalerevalidateexpireSuits
default5 minutes15 minutesneverUsed when you call no cacheLife
seconds30 seconds1 second1 minuteNear-real-time data
minutes5 minutes1 minute1 hourFeeds, news
hours5 minutes1 hour1 dayInventory, weather
days5 minutes1 day1 weekBlog posts, articles
weeks5 minutes1 week30 daysNewsletters, podcasts
max5 minutes30 days1 yearContent that rarely changes

Properties you omit in a custom or inline profile inherit from default. cacheLife({}) applies default as it is.

Short lifetimes change where content is served from#

A lifetime that is too short to store safely changes how the result is prerendered:

ConditionEffect
revalidate is 0, or expire is under 5 minutesExcluded from prerendering. It becomes a dynamic hole resolved at request time.
stale under 30 secondsExcluded from prerendering, because a prefetch would expire before the click.
stale from 30 seconds up to 5 minutesPrerendered, but kept out of the route's App Shell.

Of the built-in profiles only seconds crosses a threshold: its one-minute expire excludes it from prerendering. Wrap components that use it in <Suspense>.

Client stale time#

The server sends stale to the browser in the x-nextjs-stale-time response header, and the client router enforces a minimum of 30 seconds. A revalidateTag, revalidatePath, updateTag or refresh call from a Server Action clears the whole client cache regardless of stale.

Nested caches#

When one cached scope uses another:

  • The outer scope has an explicit cacheLife: its own lifetime wins, shorter or longer than the inner one.
  • The outer scope has no cacheLife: it starts from default, a shorter inner lifetime lowers it, and a longer one cannot raise it.
  • A short-lived inner cache inside an outer scope without cacheLife fails during prerendering. The error exists so a third-party component using seconds cannot silently make your page dynamic. Add an explicit cacheLife to the outer scope.

cacheTag#

  • cacheTag accepts one or more strings: cacheTag('products', 'product:42').
  • Tagging the same entry twice with the same tag has no extra effect.
  • One call accepts up to 128 tags, each up to 256 characters. Longer tags are skipped, tags past the 128th are dropped, and both log a warning.
  • You can call it after loading data, to tag with values from the result.

Caching implications#

  • One cacheLife call runs per invocation. You may call it in different branches, but only one branch should run.
  • Changing a built-in in config changes every call site. Redefining default also changes scopes that call no cacheLife at all.
  • Tags work across stores. An invalidated tag affects the server entry, the prerendered page that included it, and, when called from a Server Action, the browser's cached copy.

Common patterns#

Declare custom profiles in next.config.ts#

next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  cacheLife: {
    catalog: {
      stale: 300, // 5 minutes in the browser
      revalidate: 1800, // refresh in the background after 30 minutes
      expire: 86400, // after a quiet day, wait for fresh data
    },
    editorial: {
      stale: 600, // 10 minutes
      revalidate: 3600, // 1 hour
      expire: 604800, // 1 week
    },
  },
};

export default nextConfig;

next dev, next build and next typegen generate typed overloads of cacheLife from this config, so your editor autocompletes 'catalog' and 'editorial' and shows their values.

lib/catalog-data.ts
import { cacheLife, cacheTag } from 'next/cache';

export type CatalogItem = { sku: string; name: string; priceCents: number };

export async function getCatalogItems(): Promise<CatalogItem[]> {
  'use cache';
  cacheLife('catalog');
  cacheTag('catalog');

  const response = await fetch('https://api.example.com/catalog');
  return response.json();
}

The caching example app uses the same catalog profile.

Choose the lifetime from the data#

A draft or missing record should not be cached as long as a published one:

lib/posts.ts
import { cacheLife, cacheTag } from 'next/cache';

type Post = { slug: string; title: string; revalidateSeconds?: number };

export async function getPost(slug: string): Promise<Post | null> {
  'use cache';
  cacheTag(`post:${slug}`);

  const response = await fetch(`https://cms.example.com/posts/${encodeURIComponent(slug)}`);
  if (!response.ok) {
    // Not published yet: check again soon.
    cacheLife('minutes');
    return null;
  }

  const post: Post = await response.json();
  // Let the CMS decide, with an hour as the fallback.
  cacheLife({ revalidate: post.revalidateSeconds ?? 3600 });
  return post;
}

Long lifetime plus a tag for CMS content#

Content that changes only when someone edits it does not need a timer. Use cacheLife('max') with a tag, and have the CMS webhook call revalidateTag when content changes. The entry stays in the static shell, and nothing refreshes content that did not change. The webhook side is on Revalidation.

Common mistakes#

Omitting cacheLife. The default profile applies, and nested caches can shorten it without you noticing.

Using a custom profile name that is not in next.config.ts. The generated types reject it. Declare the profile in the config first.

Setting expire lower than revalidate. Next.js raises an error for that configuration.

Using seconds for data you expected in the static shell. Its one-minute expire makes it a dynamic hole, so it needs a <Suspense> boundary.

Expecting stale to set a Cache-Control header. It controls the Next.js client router's cache, not HTTP caching.

Calling cacheLife or cacheTag outside a cached scope, for example at the top of a module. It throws.

Building a tag from untrusted input without a limit. Tags over 256 characters are skipped with only a console warning, so that entry can never be invalidated by that name.
