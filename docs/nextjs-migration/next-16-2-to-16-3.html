Next.js 16.2 to 16.3

Rename the 16.2 error-handling APIs, drop prop drilling for root params, pick up the new build and dev defaults, and decide on the opt-in features.

NNext.jsCurrentNext.js 16.3+Targets Next.js 16.3

Overview#

Next.js 16.3 was released on 3 August 2026. For most apps the upgrade is small: two experimental names from 16.2 became stable under new names, and several performance features turned on by default. The larger part of 16.3, Instant Navigations, is opt-in and changes nothing until you enable it.

ChangeKindAction needed
unstable_catchError → catchErrorRename (stable)Yes, if you used it
unstable_retry → retry on error.tsx / global-error.tsxRename (stable)Yes, if you used it
Root params from next/root-paramsNewOptional: remove prop drilling
Turbopack filesystem cache for next buildNew defaultCheck CI caches .next/cache
Dev memory evictionNew defaultNone
TypeScript 7 for next build type checkingNew optionOptional
Native Node.js streams in App Router SSRInternalNone
Small prefetch payloads bundled togetherNew defaultNone
import.meta.glob in TurbopackNewOptional
Instant Navigations (partialPrefetching)Opt-inOptional
Rust React Compiler, network resilienceExperimentalOptional

Warning

Do not stop at 16.3.0. Install next@16.3.5. 16.3.0 to 16.3.2 are affected by the August 2026 Security Release, which is fixed in 16.3.3. See Security releases between 16.2 and 16.3 below.

Coming from 15.x? Do Next.js 15 to 16 first.

Upgrade#

bash
npm install --save-exact next@16.3.5 eslint-config-next@16.3.5

Or let the codemod pick the version and prompt for transforms:

bash
npx @next/codemod@canary upgrade latest

unstable_catchError is now catchError#

16.2 shipped unstable_catchError() as an experimental way to build an error boundary anywhere in the tree. 16.3.0 made it stable as catchError, and the unstable_retry field it passed became retry. Both old names are gone from the 16.3 docs.

The type also matters. ErrorInfo.error is typed unknown in 16.3.5, because anything can be thrown. The 16.2 and 16.3 release posts read error.message directly, which does not type-check. Narrow it first.

app/dashboard/revenue-boundary.tsxlegacy
'use client';

import { unstable_catchError, type ErrorInfo } from 'next/error';

function RevenueFallback(props: { title: string }, { error, unstable_retry }: ErrorInfo) {
  return (
    <div role="alert">
      <h2>{props.title}</h2>
      <p>{error.message}</p>
      <button onClick={() => unstable_retry()}>Try again</button>
    </div>
  );
}

export default unstable_catchError(RevenueFallback);
app/dashboard/revenue-boundary.tsx
'use client';

import { catchError, type ErrorInfo } from 'next/error';

function RevenueFallback(props: { title: string }, { error, retry }: ErrorInfo) {
  const message = error instanceof Error ? error.message : 'Something went wrong.';

  return (
    <div role="alert">
      <h2>{props.title}</h2>
      <p>{message}</p>
      <button type="button" onClick={() => retry()}>
        Try again
      </button>
    </div>
  );
}

export default catchError(RevenueFallback);

catchError must be called from a Client Component, and it does not swallow notFound() or redirect(). That second point is why it exists: a hand-written React error boundary catches the special errors those functions throw. Details are on catchError; the underlying React idea is error boundaries.

unstable_retry is now retry#

The same rename applies to the props of error.tsx and global-error.tsx. retry() re-fetches and re-renders the segment, including its Server Components. Prefer it over reset(), which only clears client error state and therefore cannot recover from a failed server render.

app/dashboard/error.tsxlegacy
'use client';

import type { ErrorInfo } from 'next/error';

export default function DashboardError({ error, unstable_retry }: ErrorInfo) {
  return (
    <div>
      <p>{error.message}</p>
      <button onClick={() => unstable_retry()}>Try again</button>
    </div>
  );
}
app/dashboard/error.tsx
'use client';

import type { ErrorInfo } from 'next/error';

export default function DashboardError({ error, retry }: ErrorInfo) {
  const message = error instanceof Error ? error.message : 'The dashboard failed to load.';

  return (
    <div role="alert">
      <p>{message}</p>
      <button type="button" onClick={() => retry()}>
        Try again
      </button>
    </div>
  );
}

Find every remaining use before you build:

bash
grep -rnE "unstable_(catchError|retry)" app src

Root params replace prop drilling#

Dynamic segments above the root layout, such as app/[lang], are effectively global: nearly every component needs them. Before 16.3 the documented way to reach them deep in the tree was to read params in the page and pass the value down as a prop through every level.

16.3 generates one async getter per root segment in next/root-params. Any Server Component can call it, including inside a "use cache" scope.

app/[lang]/posts/[slug]/page.tsx
async function PostFooter({ lang }: { lang: string }) {
  return <footer>{lang === 'fr' ? 'Merci de votre lecture' : 'Thanks for reading'}</footer>;
}

export default async function PostPage(props: PageProps<'/[lang]/posts/[slug]'>) {
  const { lang, slug } = await props.params;

  return (
    <article>
      <h1>{slug}</h1>
      <PostFooter lang={lang} />
    </article>
  );
}
app/[lang]/posts/[slug]/page.tsx
import { lang } from 'next/root-params';

async function PostFooter() {
  const language = await lang();
  return <footer>{language === 'fr' ? 'Merci de votre lecture' : 'Thanks for reading'}</footer>;
}

export default async function PostPage(props: PageProps<'/[lang]/posts/[slug]'>) {
  const { slug } = await props.params;

  return (
    <article>
      <h1>{slug}</h1>
      <PostFooter />
    </article>
  );
}

The export only exists because a root layout lives under the dynamic segment:

app/[lang]/layout.tsx
import { lang } from 'next/root-params';

export default async function RootLayout(props: LayoutProps<'/[lang]'>) {
  return (
    <html lang={await lang()}>
      <body>{props.children}</body>
    </html>
  );
}

export async function generateStaticParams() {
  return [{ lang: 'en' }, { lang: 'fr' }];
}

Limits to know before you refactor:

  • Server Components only. Not in Client Components, Server Actions or Route Handlers. Route Handler support is planned. Keep reading params there.
  • Segment names must be valid identifiers. [post-slug] fails.
  • With Cache Components, every root param needs at least one value from generateStaticParams, or the build fails.

unstable_rootParams() was removed in 16.0; next/root-params is its replacement. See Root params.

PageProps, LayoutProps and RouteContext#

The route-aware helpers are global types. You do not import them. next dev, next build and next typegen generate them, together with the next/root-params exports, from the folders that actually exist. If you still hand-write { params: Promise<{ slug: string }> }, switch while you are here: a renamed folder then becomes a type error instead of an undefined at runtime.

app/api/items/[id]/route.ts
export async function GET(_request: Request, context: RouteContext<'/api/items/[id]'>) {
  const { id } = await context.params;
  return Response.json({ id });
}

In CI, generate the types before type checking, since tsc alone does not know about them:

bash
npx next typegen && npx tsc --noEmit

See Typed routes.

Build and dev defaults#

The Turbopack filesystem cache now applies to next build, on by default. It was on for next dev since 16.1. Repeat builds read unchanged artifacts from .next/cache/turbopack. Vercel reported up to 5.5x faster cached builds on some projects.

The benefit only appears if .next/cache survives between builds. Configure your CI to restore it. If your build environment never keeps it, turn off the build cache so Next.js does not write a cache that is never read:

next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  experimental: {
    // The cache behavior is on by default in 16.3; only the key lives under `experimental`.
    turbopackFileSystemCacheForBuild: false,
  },
};

export default nextConfig;

Dev memory eviction is on by default too. Once Turbopack has written its cache to disk it can drop the in-memory copy, and the 16.3 post reports up to 90% less memory in long next dev sessions. The key that tunes it, experimental.turbopackMemoryEviction ('auto' by default, or 'full' or false), is labelled experimental.

Prefetch inlining bundles small prefetch responses into one request. The behavior is a permanent part of the App Router; only its tuning key, experimental.prefetchInlining, is experimental.

See Dev memory and caching.

TypeScript 7#

next build runs the project-local tsc CLI for type checking. That is what makes TypeScript 7 usable, since TypeScript 7 does not ship the JavaScript compiler API. To opt in, install it:

bash
npm install --save-dev typescript@^7

No config change is needed. Two things differ from the API-based checker: the diagnostics are tsc's own, without Next.js code frames, and the whole project selected by tsconfig.json is checked, including tests.

Warning

Experimental. The switch between the CLI checker and the compiler API is experimental.useTypeScriptCli (default true). Setting it to false while TypeScript 7 is installed makes next build exit.

Instant Navigations#

Note

Opt-in (16.3). Instant Navigations need cacheComponents: true and the top-level partialPrefetching: true. These behaviors are slated to become the default in a future major version, but in 16.3 nothing changes until you set both flags.

next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
};

export default nextConfig;

The suite is Partial Prefetching (one reusable App Shell per route instead of one prefetch per link), improved ISR (a page not prerendered at build serves an instant shell on its first visit, then upgrades in the background), Instant Insights and the Navigation Inspector in the Next.js DevTools, and the instant() Playwright helper from @next/playwright. The helper's own README marks instant() as experimental and not yet stable, and running it against next start needs experimental.exposeTestingApiInProductionBuild: true.

Two 16.3 codemods help an existing app get there:

CodemodUse it when
npx @next/codemod@canary cache-components-instant-false ./appYou are enabling cacheComponents. It adds export const instant = false to every page, layout and default, so the app builds, and you remove the opt-outs route by route.
npx @next/codemod@canary remove-partial-prefetch ./appYou opted routes in one at a time with export const prefetch = 'partial' and now set partialPrefetching: true globally.

Pass ./src/app in a src/ project. A wrong path reports 0 ok instead of failing. If you are not on Cache Components yet, start with The pre-16 caching model, then read Instant Navigations.

Experimental features#

Warning

Experimental. experimental.turbopackRustReactCompiler runs a native Rust port of the React Compiler inside Turbopack instead of the Babel plugin. It requires reactCompiler: true, works only with Turbopack, and needs no babel-plugin-react-compiler.

next.config.ts
import type { NextConfig } from 'next';

const nextConfig: NextConfig = {
  reactCompiler: true,
  experimental: {
    turbopackRustReactCompiler: true,
  },
};

export default nextConfig;

Warning

Experimental. experimental.useOffline keeps navigations, prefetches and Server Actions pending while the network is down and retries them when it returns. It also makes the useOffline hook from next/offline report the state. Without the flag the hook always returns false.

app/offline-banner.tsx
'use client';

import { useOffline } from 'next/offline';

export function OfflineBanner() {
  const isOffline = useOffline();
  if (!isOffline) return null;
  return <div role="status">You are offline. Retrying when you reconnect.</div>;
}

io() from next/cache arrived in 16.3.0. Under Cache Components, await io() before new Date(), Math.random() or a synchronous database driver keeps that value out of the static shell.

Common mistakes#

  • Renaming the import but not the destructured field. catchError with { unstable_retry } compiles only if retry is also renamed.
  • Reading error.message without narrowing. ErrorInfo.error is unknown. Copying the release post's snippet fails tsc.
  • Calling a root param getter in a Route Handler or Server Action. It is not supported there yet. Read params from the route context instead.
  • Calling partialPrefetching: true without cacheComponents. next dev and next build throw at config validation.
  • Describing Instant Navigations as the 16.3 default. It is opt-in in 16.3.
  • Expecting faster CI builds without caching .next/cache. The build cache lives there.
  • Stopping at 16.3.0. The August advisories affect it. Use 16.3.5.
